# ideal-harness MVP 面试题一问一答

> 适用范围：v0.2.0 / P1「可对话 MVP」
>
> 本文基于当前仓库实际实现整理。P2 安全纵深、P3 上下文工程和 P4 会话产品化中的部分能力仍属于后续规划，不应在面试中描述为已经完成。

## 一、项目概览

### Q1：请介绍一下这个项目。

**参考回答：**

这是一个 Rust 实现的 LLM Agent Harness 原型，目标是把不可靠的模型输出转换成可靠、可审计、可恢复的系统行为。

MVP 阶段主要完成了四部分：

1. 统一的 protocol 层，定义 Event、ErrorCode、ErrorEnvelope 等跨模块契约；
2. OpenAI 兼容的 HTTP + SSE 流式模型客户端；
3. Agent 工具调用闭环，即模型请求工具、系统执行工具、回传结果并继续采样；
4. 带 JSONL 事件持久化、跨轮历史和崩溃恢复能力的 `ideal-harness chat` 命令。

项目的核心设计原则是 protocol-first、事件溯源、错误按稳定 code 路由，以及 fail-closed。

### Q2：这个 MVP 的核心用户流程是什么？

**参考回答：**

用户输入后，系统创建一个 turn，并调用模型。模型如果直接返回文本，本轮结束；如果返回 tool call，系统就查找并校验工具，执行工具，将工具结果写入事件流并回传模型，之后继续采样，直到得到最终文本或达到最大工具轮次。

```text
用户输入
  → 创建 Turn
  → 调用模型并接收 SSE 流
  → 返回文本？是：结束本轮
  → 返回 tool_call？
      → 查找工具
      → 校验参数
      → 执行工具
      → 写入 ToolResultAdded
      → 把结果回传模型
      → 继续采样
  → 写入最终事件或 TurnAborted
```

### Q3：为什么选择 Rust？

**参考回答：**

主要有三个原因：

- 类型系统适合约束协议、事件和状态机；
- 单二进制便于 CLI 分发；
- 对文件、进程、沙箱和底层资源控制能力较强。

代价是开发效率和库生态不如 Python 或 TypeScript，因此项目通过固定 crate 边界、统一协议和明确依赖方向来控制复杂度。

## 二、架构与模块设计

### Q4：为什么单独设计 `protocol` crate？

**参考回答：**

`protocol` 是跨 crate 的唯一契约，定义了 Event、ErrorCode、ErrorEnvelope、ModelCallSpec 等公共结构。模型客户端、Agent loop、session 和未来的 Web/TUI 客户端都围绕这份契约工作。

这样可以避免不同模块各自维护一份协议，保证序列化格式一致，也方便跨进程通信、事件重放和版本兼容。

### Q5：为什么不让各个模块直接共享内部 struct？

**参考回答：**

直接共享内部 struct 会增加耦合，导致内部实现变更容易破坏其他模块，也不利于协议版本管理。通过 protocol 层可以明确区分“内部实现类型”和“对外 wire 契约”。

### Q6：当前 crate 如何分工？

**参考回答：**

`protocol` 负责公共协议；`model-provider` 负责 OpenAI 兼容模型通信；`agent-loop` 负责主循环和工具调用闭环；`tools` 负责工具注册、参数校验和调度；`session` 负责 JSONL 事件追加、重放和 fork；`context` 负责 token 预算和压缩判定；`approval` 和 `sandbox-policy` 提供安全抽象；`harness-cli` 负责装配和命令行入口。

依赖方向是从底层契约逐步向上层装配，避免反向依赖。

## 三、Agent Loop 与工具调用

### Q7：Agent loop 是如何工作的？

**参考回答：**

Agent loop 维护当前 turn 的阶段状态。它先记录用户输入并调用模型，然后根据模型返回结果决定下一步：有文本就完成本轮，有工具调用就进入工具调度阶段。工具执行结果写入事件流后，再回到模型采样阶段。

这种设计将“模型决策”和“系统执行”分开，模型只能提出工具调用请求，真正的执行必须经过注册表和参数校验。

### Q8：为什么工具调用后还要继续采样？

**参考回答：**

模型返回 tool call 只是请求系统执行工具，并不是最终答案。完整流程是：

```text
模型：调用 weather 工具
系统：执行 weather
工具：返回天气结果
系统：把结果回传模型
模型：根据结果生成最终文本
```

因此工具结果必须重新进入模型上下文，模型才能基于真实执行结果回答用户。

### Q9：如何防止模型无限调用工具？

**参考回答：**

系统为一个 turn 设置 `max_tool_rounds`。每完成一轮工具调用后计数，如果超过上限，就追加 `TurnAborted` 事件并终止本轮。

这样既避免模型死循环，也保证异常终止可以在事件流中追踪。

### Q10：如何保证 `tool_call` 和 `tool_result` 配对？

**参考回答：**

每个工具调用都有明确的 call id，工具结果使用对应的 id 回填。无论工具成功、未知工具、参数非法还是 handler 失败，系统都生成对应的工具结果，而不是直接丢弃调用。

这样可以保证模型请求和系统结果始终成对，后续做上下文裁剪时也不会破坏消息语义。

### Q11：未知工具如何处理？

**参考回答：**

未知工具不能触发任何 handler，也不能让整个进程崩溃。系统会生成结构化的失败结果，并使用稳定错误码告知模型，让模型有机会修正工具名称或重新规划。

### Q12：非法工具参数如何处理？

**参考回答：**

工具执行前先进行参数校验。校验失败时不调用 handler，而是构造 `ToolOutcome::Failure`，写入工具结果事件，再把错误反馈给模型。

当前 MVP 的校验器是骨架版本，主要检查参数是否为 object，以及 required 字段是否存在。完整的 `type`、`enum`、`items`、`additionalProperties` 等校验属于后续 TASK-201。

### Q13：为什么参数错误不是直接让整个 turn 失败？

**参考回答：**

参数错误通常是模型可以修正的问题。将它作为工具失败结果回传模型，可以让模型自纠；只有模型调用失败、达到最大轮次等情况，才需要终止整个 turn。

## 四、流式模型客户端

### Q14：SSE 流式响应如何解析？

**参考回答：**

客户端逐行读取 SSE 响应，识别 `data:` 数据行、结束标志和 JSON 内容。每个 chunk 中提取文本增量、tool call 片段和 finish reason，最后聚合成一次完整的模型回复。

### Q15：为什么 `tool_calls` 需要聚合？

**参考回答：**

模型可能把一次工具调用拆分到多个 SSE chunk 中，例如第一个 chunk 返回 id，后续 chunk 返回函数名和分段参数。因此客户端需要按 `index` 聚合：id 和 name 取首个非空值，arguments 按顺序拼接，最后再构造完整的工具调用请求。

### Q16：流式过程中断了怎么办？

**参考回答：**

超时、半途连接关闭、响应截断、非 JSON 数据行等情况统一映射为 `ModelStreamBroken`，不能静默跳过。Agent loop 收到错误后结束当前 turn，并写入失败事件，确保问题可追踪。

### Q17：为什么错误控制流不能解析 message 字符串？

**参考回答：**

message 面向人，可能变化、国际化或补充上下文；`ErrorCode` 面向机器，是稳定契约。

例如上下文超限应该匹配 `ContextWindowExceeded`，然后触发压缩或重试，而不是判断 message 是否包含“context length”。

### Q18：API key 如何处理？

**参考回答：**

客户端从环境变量 `IDEAL_HARNESS_API_KEY` 读取 API key。key 缺失或为空时直接拒绝启动模型调用，采用 fail-closed 策略，不使用默认值，也不把 key 写入事件或错误信息。

## 五、事件溯源与会话恢复

### Q19：为什么使用 JSONL 事件流，而不是只保存最终对话文本？

**参考回答：**

Agent 的执行过程不仅包括用户消息和最终答案，还包括模型增量、工具调用、工具结果、失败和中止。JSONL 事件流可以保留完整轨迹，支持 replay、崩溃恢复和审计。

最终对话历史只是事件流的一种投影，而不是唯一数据源。

### Q20：JSONL 会话如何保证序号连续？

**参考回答：**

创建或重新打开会话时，系统读取已有事件并计算最后序号。后续 append 从当前序号继续递增，因此进程异常退出后重新打开仍可以继续追加。

### Q21：程序在一个 turn 中途崩溃，恢复时怎么办？

**参考回答：**

重新打开会话时检查是否存在未完成的 turn。如果存在，就补写 `TurnAborted`，而不是把悬空 turn 误判为成功完成。这样可以避免异常状态影响后续历史重建。

### Q22：为什么事件流中的坏行不能直接跳过？

**参考回答：**

静默跳过会造成审计信息丢失，也可能让后续状态与真实执行过程不一致。事件流是唯一真相源，因此遇到损坏行应该返回错误，让调用方明确知道会话无法完整恢复。

### Q23：当前跨轮历史如何构建？

**参考回答：**

MVP 会从事件流中恢复用户消息和最终 assistant 文本，形成后续模型可见的 `chat_history`。工具调用中间态暂时由该 turn 的最终文本概括，完整的工具结果压缩和 spill 属于后续上下文工程阶段。

### Q24：fork 如何实现？

**参考回答：**

session 层支持按指定 boundary 将源 JSONL 的事件前缀复制到目标会话，目标会话从这个种子继续追加，源会话不受影响。

不过 `resume` 和 `fork` 的完整 CLI 产品入口属于 P4 任务，底层能力和命令行产品化要区分开来。

## 六、错误处理与安全原则

### Q25：什么是 fail-closed？项目中有哪些体现？

**参考回答：**

fail-closed 指的是服务缺失、参数不完整或状态不明确时默认拒绝，而不是默认放行。

当前 MVP 中包括：API key 缺失时拒绝启动；审批器不存在时拒绝提权；非法工具参数不执行 handler；模型流断开时终止当前 turn 并留痕。

### Q26：为什么审批服务不存在时必须拒绝？

**参考回答：**

如果没有审批服务却默认允许提权，系统就会在最不确定的情况下获得更高权限，这会把基础设施缺失变成安全漏洞。拒绝虽然会牺牲部分可用性，但符合安全系统的 fail-closed 原则。

### Q27：当前 MVP 是否已经具备完整沙箱？

**参考回答：**

还没有。当前已有三档 `SandboxMode` 抽象、词法路径栅栏和提权方向校验，但还没有 Windows Restricted Token、Linux Landlock、受限执行进程池和网络白名单代理。

这些属于 P2 的 TASK-202 和 TASK-203，不能把当前策略抽象描述成完整 OS 沙箱。

## 七、测试与工程质量

### Q28：你如何测试 Agent loop？

**参考回答：**

主要使用 mock provider 覆盖不同模型行为：

- 普通文本回复；
- 文本 → 工具 → 文本；
- 未知工具；
- 非法参数；
- 参数错误时 handler 不应被调用；
- 模型失败；
- 超过最大工具轮次；
- 跨轮历史记忆；
- 完整事件生命周期。

### Q29：为什么必须测试失败路径？

**参考回答：**

Agent 系统的风险通常不在正常回答，而在模型异常、工具失败、流式断开和上下文超限。如果失败路径没有测试，很容易出现静默失败、错误放行或事件缺失。因此依赖 `ModelProvider`、`Approver` 等 trait 的逻辑必须有故障注入测试。

### Q30：当前项目的质量门禁是什么？

**参考回答：**

当前仓库要求 build、workspace test、clippy 和 fmt 通过。实际检查结果为：

- `cargo build --workspace --offline`：通过；
- `cargo test --workspace --offline`：通过，当前输出为 51 passed、0 failed；
- `cargo clippy --workspace --all-targets --offline -- -D warnings`：通过；
- `cargo fmt --all -- --check`：通过。

## 八、项目边界与技术债

### Q31：这个 MVP 还缺哪些能力？

**参考回答：**

主要缺口包括：

- 完整 JSON Schema 校验；
- OS 级受限执行进程池；
- 默认断网和网络白名单代理；
- 终端 y/n 人工审批通道；
- 提权字段动态 Schema 广告的完整集成；
- 上下文溢出后的自动压缩和重试；
- 超长工具结果 spill；
- SQLite 投影；
- 完整的 `resume` / `fork` CLI 子命令。

### Q32：如果继续开发，你会优先做什么？

**参考回答：**

我会优先完成 P2 安全纵深。具体顺序可以是先补完整 JSON Schema 校验，再实现人工审批和动态 Schema 广告，最后实现受限进程池与网络白名单代理。

原因是工具参数校验和权限出口是 Agent 安全边界的基础，而 OS 隔离和网络隔离会涉及更多平台差异和集成测试。

### Q33：当前实现有哪些技术债？

**参考回答：**

主要技术债有：

- `context` 和部分安全能力仍是骨架；

## 九、容易被追问的开放问题

### Q34：如果工具执行超时，应该如何处理？

**回答思路：**

需要为工具执行增加超时和取消语义。超时后不能无限等待，应生成结构化失败结果并记录事件；如果工具有副作用，还需要考虑进程隔离和幂等设计。

### Q35：如果模型重复调用同一个有副作用的工具怎么办？

**回答思路：**

不能只依赖 `max_tool_rounds`。还需要工具声明副作用级别、调用幂等键、审批策略和必要的重复调用检测。P2 的沙箱和审批能力完成后，可以把这些策略接入统一权限边界。

### Q36：JSONL 多进程并发追加如何保证安全？

**回答思路：**

MVP 主要面向单进程追加。生产化时需要引入文件锁、单写者队列或专门的 session writer，并确保序号分配和事件写入具有原子性。

### Q37：工具结果很大时如何避免撑爆上下文？

**回答思路：**

后续应采用 spill：完整结果落盘，事件中只保留预览和 locator；当上下文接近预算时，先裁剪工具结果，再做 LLM 摘要，同时保证 tool_call 和 tool_result 配对不被拆开。

### Q38：当前实现是否支持多个并行 tool call？

**回答思路：**

SSE 解析层已经可以按 index 聚合多个 tool call，但工具执行调度的并行性、顺序、失败隔离和副作用语义还需要进一步设计，不能简单等同于已经具备完整并行执行能力。

## 十、60 秒项目介绍模板

> 我做的是一个 Rust Agent Harness MVP，目标是把 LLM 的不确定输出约束成可追踪、可恢复的系统行为。架构上采用 protocol-first，跨模块数据统一通过 Event 和 ErrorCode 表达；底层用 JSONL 做事件溯源，支持会话恢复和 replay；模型侧实现了 OpenAI 兼容 SSE 客户端，并处理了流式 tool call 分片聚合；Agent loop 支持模型调用工具后继续采样，直到得到最终文本，同时有最大工具轮次保护和失败事件留痕。当前 P1 可对话 MVP 已完成，下一阶段重点是 OS 沙箱、网络白名单和人工审批。
